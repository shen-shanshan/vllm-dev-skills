# DP2 prefill delayer 调优结果（DSv4.1-Flash，2× MI355X，AgentX）

计划见 `../../dp2_delayer_tuning_plan.md`。

**测试条件：**
- 代码：vLLM `dp-prefill-delayer` `2921e6e5c2`（base 为 main `feb4cb019f`），`vllm-rs` 用同一份代码编译；
- 部署：TP1 × DP2，MoE 在两个 rank 上做 TP 切分，16K budget，DSpark 5（synthetic AL 3.51），consistent-hash router；
- 负载：c128。F 开头的点用快速模式（1200 s，warmup 每条 lane 1 个请求），S 开头的点跑 3600 s；
- 复现：`perf/run_sweep.sh`，汇总表用 `perf/compare.py` 生成；
- 原始结果在 `results/<tag>/`。备份时没有保留 AIPerf 的 server metrics 和 timeslices 文件，每个点约 200 MB。

| delayer FIRE 原因 | — | no_prefill 11%，max_wait 6%，fill 5% |

**和 leader 的 3600 s 数据对照**（快速模式 vs 3600 s）：

| 指标 | 快速模式（本次） | 3600 s（leader） |
|---|---|---|
| 吞吐提升 | +6.6% | +4% |
| p90 interactivity | 25.5 → 35.7（+40%） | 28.8 → 35.6（+24%） |
| TTFT p90 | 1.39 → 5.06 s | 1.2 → 4.2 s |

- **方向一致，量级接近**，可以用快速模式继续筛选参数。
- 差异主要在默认调度器一侧：快速模式下 prefix cache 还没热，默认调度器的 ITL p90 更差（39.2 ms，leader 是约 34.7 ms），绝对吞吐也偏低（186K，leader 是 218K）。所以快速模式会放大 delayer 带来的相对收益。
- **快速模式下的 TTFT 门槛要相应放宽。** 快速模式下 TTFT 整体偏高，连默认调度器 TTFT 超过 10 s 的请求也有 1.2%，按原来 3600 s 的门槛（TTFT p90 ≤ 5 s，超过 10 s 的请求 ≤ 1%），连 baseline 都过不了。因此按本阶段测得的偏移量折算：
  - TTFT p90 上限：3600 s 下 leader 配置是 4.2 s，快速模式下是 5.06 s，比例约 1.2，所以 5 s × 1.2 = **6 s**；
  - 超过 10 s 的请求：默认调度器在 3600 s 下约 0.3%～0.5%，快速模式下是 1.2%，大约高 1 个百分点，所以 1% + 1 个百分点，取 **2.5%**。
- **E2E-norm interactivity p90 略降**（22.5 → 21.3）：TTFT 拉长了，最慢的那批请求端到端反而变慢。后续需要关注这一点。

## 第 1 阶段：interval N（c128，W=5000，快速模式）

| 指标 | F0 默认调度器 | F2 N6 | F1 N11 | F3 N16 |
|---|---:|---:|---:|---:|
| 请求数 / 错误 | 4523 / 0 | 4799 / 1 | 4762 / 0 | 4803 / 0 |
| 总吞吐 / GPU（tok/s） | 186,066 | 200,036（+7.5%） | 198,362（+6.6%） | 201,610（+8.4%） |
| TTFT p50 / p90 / p99（s） | 0.32 / 1.39 / 15.79 | 0.91 / 4.05 / 10.45 | 1.17 / 5.06 / 19.16 | 1.47 / 5.51 / 20.54 |
| TTFT > 10 s 的请求 | 1.2% | 1.1% | 2.1% | 1.6% |
| ITL p50 / p90 / p99（ms） | 25.6 / 39.2 / 117.7 | 22.4 / 30.1 / **58.8** | 21.6 / 28.0 / 78.7 | 20.4 / 27.6 / 77.5 |
| p90 interactivity | 25.5 | 33.2 | 35.7 | **36.3** |
| E2E-norm interactivity p50 / p90 | 36.85 / 22.52 | 39.02 / **23.25** | 39.45 / 21.33 | 39.60 / 19.95 |
| E2E latency mean / p90（s） | 23.9 / 55.5 | 21.7 / 45.7 | 21.8 / 48.2 | 21.6 / 47.0 |
| delayer HOLD 占比 | — | 72%（align 40%，protected 26%） | 78%（protected 47%，align 28%） | 81%（protected 61%，align 19%） |

**结论：**
- **吞吐：** 三个 N 都比默认高 7%～8%，彼此之间的差距在噪声以内（7.5%）。
- **p90 interactivity：** 随 N 增大而上升，但收益递减。N6 → N11 是 +7.5%，超过噪声；N11 → N16 只有 +1.7%，在噪声以内。所以不加测 N=24。
- **TTFT 门槛**（快速模式：p90 ≤ 6 s，超过 10 s 的请求 ≤ 2.5%）：三个 N 都满足。N 越大 TTFT 越差。
- **N6 的长尾最好：**
  - ITL p99 是 58.8 ms，N11 和 N16 约 78 ms；
  - TTFT p99 是 10.5 s，N11 和 N16 约 19～20 s；
  - E2E-norm interactivity p90 是唯一高于默认调度器的。

  原因在于 N 小时保护期短，TTFT 的长尾更短。代价是 p90 interactivity 比 N11 低 7%。
- **按规则选 N\* = 16：** 吞吐都在噪声以内，所以先比 p90 interactivity，N16 最高；N16 和 N11 的 interactivity 又在噪声以内，再比吞吐，还是 N16 高。但 N16 和 N11 基本打平，N11 作为第二名，进入第 4 阶段一起用 3600 s 确认。

## 第 2 阶段：max-wait W（c128，N=16，快速模式）

| 指标 | F0 默认调度器 | F4 W3000 | F3 W5000 | F5 W8000 |
|---|---:|---:|---:|---:|
| 请求数 / 错误 | 4523 / 0 | 4702 / 2 | 4803 / 0 | 4775 / 2 |
| 总吞吐 / GPU（tok/s） | 186,066 | 195,304（+5.0%） | 201,610（+8.4%） | 200,854（+7.9%） |
| TTFT p50 / p90 / p99（s） | 0.32 / 1.39 / 15.79 | 1.37 / 4.12 / 17.60 | 1.47 / 5.51 / 20.54 | 1.69 / **7.47** / 25.39 |
| TTFT > 10 s 的请求 | 1.2% | 1.7% | 1.6% | **3.5%** |
| ITL p50 / p90 / p99（ms） | 25.6 / 39.2 / 117.7 | 21.5 / 31.2 / 96.3 | 20.4 / 27.6 / 77.5 | 20.4 / 25.7 / 71.4 |
| p90 interactivity | 25.5 | 32.1 | 36.3 | 39.0 |
| E2E-norm interactivity p50 / p90 | 36.85 / 22.52 | 38.01 / 20.10 | 39.60 / 19.95 | 39.44 / 17.47 |
| delayer HOLD 占比 | — | 75%（protected 55%） | 81%（protected 61%） | 81%（protected 62%） |
| delayer FIRE 原因 | — | no_prefill 13%，max_wait 8%，fill 4% | no_prefill 8%，max_wait 6%，fill 4% | no_prefill 9%，max_wait 6%，fill 4% |

**结论：**
- **W8000 被淘汰：** TTFT p90 是 7.47 s，超过 10 s 的请求占 3.5%，两项都超出快速模式的门槛（6 s、2.5%）。p90 interactivity 虽然最高（39.0），但它的 E2E-norm interactivity p90 也最差（17.5）。
- **W3000 不划算：** 相比 W5000，p90 interactivity 低 11.6%，超出噪声，吞吐也低 3%，换来的 TTFT 改善却很有限：p90 从 5.5 s 降到 4.1 s，p99 和超过 10 s 的占比基本没变。拿它和第 1 阶段的 **N6 W5000** 比，N6 W5000 在吞吐、interactivity、TTFT p90/p99 和 ITL p99 上全面占优。**要压 TTFT，减小 N 比减小 W 更有效。** W 调小时，max_wait 触发的放行会更频繁（6% → 8%），但它打断的是保护期，ITL p99 因此明显变差（77.5 → 96.3 ms）。
- **W\* = 5000。** 冠军配置仍然是 **N16 W5000**，第二名是 N11 W5000。
- **请求报错：** 6 个快速模式点里共有 5 个请求报 `InvalidInferenceResultError`，即服务端返回里没有任何实际内容，都发生在开了 delayer 的点上，占比约 0.04%。默认调度器的 F0 是 0 个。数量太少，目前还不能确定和 delayer 有关，先记录下来，后续单独排查。

## 第 3 阶段：token budget（c128，N16 W5000，快速模式）

| 指标 | F0 默认调度器 | F3 16K | F6 24K | （对照）F2 N6 W5000 16K |
|---|---:|---:|---:|---:|
| 请求数 / 错误 | 4523 / 0 | 4803 / 0 | 4779 / 4 | 4799 / 1 |
| 总吞吐 / GPU（tok/s） | 186,066 | 201,610（+8.4%） | 199,704（+7.3%） | 200,036（+7.5%） |
| TTFT p50 / p90 / p99（s） | 0.32 / 1.39 / 15.79 | 1.47 / 5.51 / 20.54 | 1.38 / **4.68 / 11.02** | 0.91 / 4.05 / 10.45 |
| TTFT > 10 s 的请求 | 1.2% | 1.6% | 1.1% | 1.1% |
| ITL p50 / p90 / p99（ms） | 25.6 / 39.2 / 117.7 | 20.4 / 27.6 / 77.5 | 21.3 / 28.1 / 86.0 | 22.4 / 30.1 / 58.8 |
| p90 interactivity | 25.5 | 36.3 | 35.6 | 33.2 |
| E2E-norm interactivity p50 / p90 | 36.85 / 22.52 | 39.60 / 19.95 | 39.22 / 21.55 | 39.02 / 23.25 |
| delayer HOLD 占比 | — | 81% | 77% | 72% |

**结论：**
- **主指标打平：** 24K 和 16K 的吞吐相差 1%，p90 interactivity 相差 2%，都在噪声以内。
- **24K 的 TTFT 长尾明显更好：** p99 从 20.5 s 降到 11.0 s，超过 10 s 的请求从 1.6% 降到 1.1%，E2E-norm interactivity p90 从 20.0 升到 21.6。代价是 ITL p99 变差（77.5 → 86.0 ms）。原因是每次放行时 prefill 的容量更大，排队的长 prompt 能更快被清空。
- 按择优规则，两项主指标都打平时取吞吐高者，结果是 16K；但两者的差距在噪声以内，所以 **16K 和 24K 都进入第 4 阶段，用 3600 s 确认**。leader 的 N11 W5000 和 N16 打平，而且他已经有 3600 s 的数据，所以先不复测，等第 4 阶段的结果出来再决定。
