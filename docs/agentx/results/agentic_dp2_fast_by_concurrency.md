## 结论

1. **c128：UMBP 略有负收益。** 吞吐 −4.7%，TTFT p90 +13%，TPOT 均值 +7%。GPU prefix 命中已经有 90%，UMBP 只恢复了 0.46% 的 prompt，带来的好处抵不过两项代价：一是 S1 的 GPU KV 少了 4.2%，二是 store 的开销。−4.7% 接近 fast 模式的噪声（约 4.5%），但多个指标的方向一致。
2. **c256：有收益。** 吞吐 +10.1%，TTFT p90 −20%，p90 interactivity +27%，实际要计算的 prompt 减少 11%。
3. **c384：收益很大。** B0 已经过载：GPU prefix 命中降到 73%，TTFT p90 达到 265 s，吞吐（143,888）甚至低于 c256。S1 从 UMBP 恢复了 21.5% 的 prompt，实际计算的 prompt 减少 49%，吞吐翻倍（291,619，是所有点里最高的），TTFT p90 降到 7.9 s。
4. **c384 的 cudagraph 上限**：1024–2048 token 的 step 只占 0.5%–0.7%，和 c256 相当，暂时不需要调高上限。
5. **c544：B0 已经崩溃，S1 也到了上限。** B0 的 GPU prefix 命中只剩 27.8%，72% 的 prompt 需要重算，吞吐只有 46,641。S1 从 UMBP 恢复了 62% 的 prompt，吞吐为 287,025，和 S1-c384（291,619）基本持平，但 TTFT p50 / p90 升到 21.9 / 58.7 s，出现了 20 次 preemption，1024–2048 token 的 step 增加到 3.6%。所以吞吐上限在 c384 附近，c544 只会增加延迟。UMBP 池子仍然没有发生淘汰。
6. **c544 S1 第一次运行挂死，原因不是 UMBP。** 第一个请求到达时，DP0 的 worker 在运行时 JIT 编译 warmup 没覆盖到的 Triton kernel（`build_prefill_chunk_metadata` 等），并且一直持有 GIL。DP1 在 `execute_dummy_batch` 里等待跨 DP 的 all_reduce，超过 `VLLM_EXECUTE_MODEL_TIMEOUT_SECONDS`（300 s）后引擎崩溃，warmup 请求全部失败。重跑时 Triton cache 已经部分预热，同样的停顿约 75 s 后恢复，结果有效。所有运行（包括 B0）都有运行时 JIT 的警告。调用栈和第一次的报错保存在 `c544_s1_hang/`。
7. **趋势**：UMBP 的收益取决于 GPU KV 放不下的程度。并发越高、GPU prefix 命中下降越多，收益越大；在 GPU KV 够用的 c128，UMBP 没有收益。

## 与 #4992 的关系

#4992 只有 1 小时的本地 c256 数据（cadence 11 时 310,739 tok/s/GPU）。fast 模式开始计时时 cache 是冷的，所以我们 B0-c256 的绝对值（250,435）不能直接和它比较。要和 #4992 比绝对值，需要用 3600 s 复测。
